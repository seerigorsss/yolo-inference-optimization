# Теоретическая часть. Оптимизация распознавания видеопотока: ONNX, TensorRT, OpenCV CUDA (Python и C++)

Актуально на ноябрь 2026: Ultralytics 8.4 (YOLO26), PyTorch 2.15, ONNX Runtime 1.32, TensorRT 11, OpenCV 5.1,
OpenVINO 2026.4.

## 1. Из чего складывается время обработки кадра

Конвейер распознавания видео:

```
декодирование кадра -> препроцессинг -> инференс сети -> постпроцессинг -> отрисовка / кодирование
  (FFmpeg, NVDEC)      (resize, поля,     (свёртки YOLO)    (порог, NMS,       (вывод, запись)
                        BGR->RGB, /255)                     пересчёт рамок)
```

При последовательной обработке `t_кадра = t_dec + t_pre + t_inf + t_post + t_out`, `FPS = 1000 / t_кадра (мс)`.
При конвейерной (этапы в разных потоках) пропускная способность ограничена самым медленным этапом:
`FPS ≈ 1000 / max(t_i)`, а задержка (latency) остаётся суммой. Для видео в реальном времени важны оба числа:
FPS — успевать за камерой (25–30 к/с), задержка — для реакции системы.

Замер в разделе 2 ноутбука (YOLO26n, CPU): инференс занимает ~80% времени кадра, поэтому на CPU в первую очередь
ускоряют сеть. На GPU инференс падает до единиц миллисекунд, и узким местом становятся декодирование,
препроцессинг и постпроцессинг в Python — здесь помогают перенос препроцессинга в модель/на GPU (раздел 3 ноутбука, здесь — п. 8)
и C++ (п. 9).

## 2. Общая схема оптимизации

PyTorch в режиме eager исполняет граф оператор за оператором из Python: накладные расходы на каждый вызов,
нет склейки операций, универсальные ядра. Поэтому для развёртывания модель **экспортируют** в статический
граф и исполняют **специализированным рантаймом** под конкретное железо:

```
PyTorch (.pt) ──export──> ONNX ──┬──> ONNX Runtime + Execution Provider (CPU, CUDA, TensorRT, OpenVINO, CoreML, DirectML, MIGraphX)
                                 ├──> TensorRT (.engine)          — NVIDIA
                                 ├──> OpenVINO IR                 — Intel/AMD CPU, Intel GPU/NPU
                                 ├──> Core ML / Core AI           — Apple
                                 └──> OpenCV DNN (CPU; CUDA в 4.x)
```

Что делают рантаймы: склейка операций (Conv+BN+SiLU в одно ядро), свёртка констант, выбор лучших ядер под
железо, переиспользование памяти, понижение точности (FP16/INT8). Отдельные «рычаги», не зависящие от рантайма:
размер входа (сжатие кадра, раздел 3 ноутбука), квантование (раздел 4), пропуск кадров, батчинг нескольких потоков,
аппаратное декодирование, асинхронный конвейер.

## 3. ONNX и ONNX Runtime

**ONNX** — открытый формат графа нейросети: список операторов стандартного набора (opset) с весами.
Экспорт из PyTorch — `torch.onnx.export` (с PyTorch 2.9 по умолчанию используется новый экспортёр на основе
`torch.export`; Ultralytics и раздел 3 ноутбука используют проверенный TorchScript-экспортёр, `dynamo=False`).
В Ultralytics: `YOLO("yolo26n.pt").export(format="onnx")`.

**ONNX Runtime (ORT)** — кроссплатформенный движок исполнения ONNX от Microsoft:
- оптимизации графа трёх уровней (basic / extended / all): свёртка констант, слияние узлов, смена раскладки памяти;
- **Execution Providers (EP)** — подключаемые бэкенды: CPU (MLAS), CUDA, TensorRT, OpenVINO, CoreML,
  DirectML, MIGraphX, QNN и др. Граф делится между EP: что не поддерживает ускоритель, выполняется на CPU;
- одинаковый API в Python, C/C++, C#, Java — модель и код переносятся между языками без изменений
  (в работе один и тот же `.onnx` запускается из Python, разделы 3–5 ноутбука, и из C++, `cpp/`);
- встроенные инструменты квантования (статическое QDQ, динамическое) — использованы в разделе 4 ноутбука;
- IOBinding — данные остаются на GPU между вызовами, без лишних копий.

Плюсы: переносимость, один файл модели на все платформы, простота. Минусы: на «родном» железе обычно уступает
вендорским движкам (TensorRT на NVIDIA, OpenVINO на Intel); скорость зависит от покрытия операторов в EP.

## 4. TensorRT (NVIDIA)

TensorRT — компилятор и рантайм NVIDIA. Сборщик (builder) разбирает ONNX и строит **движок** (`.engine`/`.plan`):
- слияние слоёв и тензоров, удаление лишних копий;
- автоподбор ядер (tactics) под конкретную модель GPU, выбор раскладки памяти;
- пониженная точность: FP16/BF16, INT8, на новых GPU — FP8/FP4; Tensor Cores;
- статическое планирование памяти, CUDA Graphs.

Движок привязан к модели GPU и версии TensorRT, строится на целевой машине (минуты), зато инференс — самый
быстрый на NVIDIA. Варианты использования: `YOLO(...).export(format="engine", quantize=16)` в Ultralytics,
утилита `trtexec`, TensorRT EP в ONNX Runtime (в работе — раздел 5 ноутбука и `cpp/ --backend ort --device trt`),
Torch-TensorRT, нативный C++ API (`IRuntime` → `ICudaEngine` → `IExecutionContext::enqueueV3`).

**Важное изменение в TensorRT 11:** сети стали только «строго типизированными» — флаги FP16/INT8 у сборщика
и калибраторы INT8 (`IInt8Calibrator`) удалены. Пониженная точность задаётся в самом ONNX: FP16 — через
ModelOpt AutoCast, INT8 — явными узлами Quantize/Dequantize (Q/DQ). Именно такой Q/DQ-граф строит
раздел 4 ноутбука (`yolo26n_int8.onnx`), поэтому он подходит и для TensorRT 10, и для 11; Ultralytics 8.4 при экспорте
в engine для TensorRT 11 сам вызывает ModelOpt.

## 5. OpenCV DNN с CUDA

Модуль `cv::dnn` читает ONNX и исполняет сеть внутри OpenCV — той же библиотеки, что уже читает видео
и рисует рамки, без дополнительных зависимостей.
- GPU: `net.setPreferableBackend(DNN_BACKEND_CUDA)` + `setPreferableTarget(DNN_TARGET_CUDA | DNN_TARGET_CUDA_FP16)`
  (cuDNN + собственные CUDA-ядра OpenCV). Есть и OpenCL/Vulkan-цели.
- Пакеты `opencv-python` из pip собраны **без CUDA**: нужна сборка из исходников с
  `WITH_CUDA=ON, WITH_CUDNN=ON, OPENCV_DNN_CUDA=ON, CUDA_ARCH_BIN=<ваша архитектура>` и модулями opencv_contrib.
- Тот же OpenCV с CUDA даёт `cv::cuda::GpuMat` и модули `cudawarping`/`cudaimgproc` для препроцессинга на GPU
  и `cudacodec` (NVDEC/NVENC) для аппаратного декодирования — весь конвейер остаётся на видеокарте.

Состояние на 2026 год: **OpenCV 5.0** (июнь 2026) получил новый DNN-движок с поддержкой > 80% операторов ONNX
(в 4.x ~22%), но он пока работает только на CPU; в **OpenCV 5.1** (ноябрь 2026) старый («классический») движок
удалён. Поэтому GPU-инференс в OpenCV сейчас — это OpenCV 4.x с CUDA или OpenCV 5, собранный с ONNX Runtime
(`ENGINE_ORT` с CUDA EP). В программе на C++ это учтено: `--device cuda` для OpenCV 5.x выдаёт предупреждение
и предлагает `--backend ort`.

Плюсы: одна библиотека на весь конвейер, простой API в Python и C++, удобен для встраиваемых систем.
Минусы: на NVIDIA заметно медленнее TensorRT; сборка с CUDA трудоёмкая; старые версии не открывают
современные модели (OpenCV 4.6 не открывает YOLO11/26 — проверено, нужна ≥ 4.10).

## 6. Замена для AMD Radeon, Apple и Intel

| Платформа | Аналог TensorRT / CUDA | Как подключить в этой работе |
|---|---|---|
| **Apple Silicon** | Metal (MPS) в PyTorch; **Core ML** — CPU/GPU/Neural Engine; с WWDC 2026 — **Core AI**, преемник Core ML | `--device mps`; `export(format="coreml")` (в Ultralytics 8.4 есть и `format="coreai"`); ONNX Runtime **CoreML EP** (раздел 5 ноутбука, C++ `--device coreml`) |
| **AMD Radeon, Linux** | ROCm (PyTorch-сборка ROCm), **MIGraphX** — графовый компилятор AMD, аналог TensorRT | PyTorch ROCm (`--device 0` работает как CUDA); `onnxruntime-migraphx` |
| **AMD Radeon, Windows** | DirectML (DirectX 12); новое развитие — Windows ML, который сам доставляет EP вендоров, в т.ч. AMD MIGraphX | `onnxruntime-directml` → DmlExecutionProvider в разделе 5 ноутбука |
| **Intel / AMD CPU, Intel GPU/NPU** | **OpenVINO** (+ NNCF для INT8) | `pip install openvino` → разделы 4 и 5 ноутбука |

DirectML официально переведён в режим поддержки (sustained engineering): работает, но новые функции
развиваются в Windows ML.

## 7. Квантование

Квантование — хранение и вычисление в меньшей разрядности: `x ≈ s · (q − z)`, где `q` — целое (INT8),
`s` — масштаб, `z` — нулевая точка.
- **FP16**: вдвое меньше модель и трафик памяти; на GPU с Tensor Cores — ускорение в разы почти без потери
  точности. На CPU без FP16-арифметики выигрыша нет (видно в разделе 4 ноутбука).
- **INT8 статическое (PTQ)**: масштабы весов считаются по весам, масштабы активаций — по **калибровочным данным**
  (MinMax, Entropy/KL, Percentile). Модель ×3–4 меньше; на CPU с VNNI/AMX и на GPU — заметное ускорение.
- **INT8 динамическое**: квантуются только веса, масштаб активаций считается на лету — подходит для
  трансформеров/LSTM, для свёрточных сетей обычно медленнее (видно в разделе 4).
- **QAT** (quantization-aware training) — дообучение с имитацией квантования; точнее PTQ, но нужно обучение.
- **Per-channel** масштабы для весов свёрток (свой масштаб на каждый выходной канал) заметно снижают ошибку.
- Формат **QDQ** (Quantize/DequantizeLinear вокруг узлов) понимают ORT, TensorRT, OpenVINO.

Что показал эксперимент (раздел 4 ноутбука):
1. Голову YOLO нельзя квантовать целиком: декодер склеивает координаты рамок (0…640 пикселей) и
   вероятности классов (0…1) в один тензор. Общий INT8-масштаб ≈ 640/255 ≈ 2.5 округляет все вероятности до 0 —
   mAP = 0 при «квантовании всего графа».
2. Квантовать только свёртки — точно, но медленнее FP32: между каждой парой свёрток данные переводятся
   float↔int8. Выигрыш появляется, когда в INT8 работает вся сеть, кроме декодера (основной вариант).
3. Схема U8S8 (активации uint8, веса int8) на x86 намного быстрее S8S8.

## 8. Сжатие изображения (уменьшение входа) и перенос препроцессинга в модель

Вычисления свёрточной сети пропорциональны числу пикселей входа: 640×384 → 320×192 даёт в 4 раза меньше
операций. Цена — потеря мелких объектов (mAP падает, раздел 3 ноутбука). На практике разрешение подбирают под размер
объектов в кадре и требуемый FPS.

В разделе 3 ноутбука сжатие встроено в граф модели: вход — «сырой» кадр uint8 `[1,H,W,3]`, дальше внутри
`BGR→RGB → AvgPool k×k (антиалиасинг) → bilinear resize → поля до кратного 32 → /255 → YOLO → пересчёт рамок`.
Плюсы: препроцессинг исполняется в нативном коде рантайма (и на GPU, если он есть), Python/C++ код только
передаёт кадр; передаётся uint8 вместо float32 (в 4 раза меньше данных по шине CPU→GPU); степень сжатия —
свойство модели, а не кода. Минус: модель привязана к разрешению видео (или нужны динамические оси).

## 9. Python или C++

Сам инференс в обоих случаях выполняется в нативном коде (ORT/TensorRT/OpenCV написаны на C++), поэтому
на CPU, где инференс занимает десятки миллисекунд, разница между Python и C++ невелика (сравните
раздел 2 ноутбука и `cpp/yolo_video`). Выигрыш C++ проявляется там, где важна каждая миллисекунда вне сети:
- на GPU инференс занимает 1–5 мс, и накладные расходы Python на препроцессинг/NMS/отрисовку становятся
  сопоставимыми или большими;
- многопоточность без GIL (декодирование, инференс, запись в разных потоках), несколько камер;
- развёртывание без интерпретатора и пакетов Python: встраиваемые системы, меньше памяти, предсказуемая задержка.
Python удобнее для экспериментов, экспорта и квантования — типичная схема: готовим модель в Python,
запускаем в продакшене из C++ тот же `.onnx`/`.engine`.

## 10. Сводное сравнение

| Способ | Железо | Python / C++ | Точности | Сильные стороны | Ограничения |
|---|---|---|---|---|---|
| PyTorch (eager) | CPU, CUDA, ROCm, MPS | да / LibTorch | FP32, FP16, BF16 | гибкость, обучение | медленнее всего, тяжёлые зависимости |
| ONNX Runtime | любое (через EP) | да / да | FP32, FP16, INT8 (QDQ) | переносимость, один API, квантование из коробки | уступает вендорским движкам на их железе |
| TensorRT | только NVIDIA | да / да | FP32, FP16, BF16, INT8, FP8, FP4 | максимальная скорость на NVIDIA | движок привязан к GPU и версии; долгая сборка; в 11.x точность только через Q/DQ/AutoCast |
| OpenCV DNN | CPU; CUDA (4.x); OpenCL/Vulkan | да / да | FP32, FP16 (CUDA) | одна библиотека на весь конвейер | CUDA — только сборка из исходников; в 5.x GPU пока нет |
| OpenVINO | Intel/AMD CPU, Intel GPU/NPU | да / да | FP32, FP16/BF16, INT8 | очень быстро на x86 CPU | не для NVIDIA/Apple GPU |
| Core ML / Core AI | Apple CPU/GPU/ANE | да / Swift, ObjC | FP16, INT8 | Neural Engine, энергоэффективность | только Apple |
| MIGraphX / DirectML | AMD Radeon | через ORT / да | FP32, FP16, INT8 | GPU AMD | экосистема беднее CUDA |

## 12. Выводы

1. Пакет Ultralytics установлен, предобученная YOLO26n распознаёт объекты на изображениях и в видеофайле
   (Python, раздел 2 ноутбука); на CPU без оптимизаций — ~16 к/с при входе 640.
2. Экспорт в ONNX — базовый и почти «бесплатный» шаг: ×1.35 к скорости без потери точности, один файл модели
   для Python и C++ и для любых ускорителей через Execution Providers.
3. Максимальная скорость достигается «родным» движком для железа: TensorRT на NVIDIA, OpenVINO на Intel
   (у нас ×4.5 к PyTorch на CPU), Core ML/Core AI на Apple, MIGraphX/DirectML на AMD. OpenCV DNN удобен тем, что
   весь конвейер остаётся в одной библиотеке; CUDA-инференс в нём — только в OpenCV 4.x, собранном с CUDA,
   а новый движок OpenCV 5 пока работает на CPU (но на CPU он заметно быстрее 4.x).
4. Квантование INT8 (статическое, QDQ, per-channel, с калибровкой) уменьшает модель в 3 раза и ускоряет её
   в 1.7 раза на CPU при потере ~1.5 пункта mAP. Критично оставить во float декодер головы детектора,
   иначе точность падает до нуля; квантование только свёрток не ускоряет из-за переходов float↔int8.
   Тот же Q/DQ-граф подходит для TensorRT 11, где неявное INT8-квантование удалено.
5. Сжатие кадра внутри модели переносит весь препроцессинг в граф: вызывающий код (Python или C++) только
   передаёт кадр. Скорость растёт пропорционально уменьшению числа пикселей (до ×3.7 при 256 px), точность на
   мелких объектах падает — разрешение выбирается под задачу.
6. Реализация на C++ даёт те же результаты и ту же скорость на CPU; её преимущества — развёртывание без Python,
   многопоточность и низкие накладные расходы, которые важны на GPU.
